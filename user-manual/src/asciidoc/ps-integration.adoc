
== Integrate a custom PS (Primärsystem)

Integrating a custom Primärsystem (PS) is a primary design goal of the TI 2.0 Testhub.
The following steps describe how to run the Testhub backend locally so that a custom PS running on the Docker host can connect to the VSDM resource server via the ZETA ingress.

=== 1. Register the service host names in `/etc/hosts`

Every service that must be reachable from outside of Docker has to be registered in `/etc/hosts` using the service name from the compose files.
This is required because the ZETA components (e.g. the OAuth protected resource metadata and the Keycloak issuer) use these host names in their URLs.

Example for the VSDM ZETA ingress:

----
127.0.0.1       vsdm-zeta-ingress
----

=== 2. Start the Testhub in `backend-only` mode

Start the Testhub with the `backend-only` profile. This disables the built-in PS simulators (VSDM Client and Card Terminal Client):

[source,bash]
----
docker compose -f ./infra/docker/compose-local.yaml --env-file=./infra/docker/.env --env-file=./infra/docker/.env-local --profile backend-only up -d --remove-orphans
----

All required local adjustments can be made in the file `infra/docker/.env-local`, which overrides the defaults from `infra/docker/.env`.
This applies in particular to the port mappings. For example, the following entry exposes the VSDM ZETA ingress on the standard HTTPS port, so it can be reached via `https://vsdm-zeta-ingress/`:

----
PORT_VSDM_ZETA_INGRESS=443
----

NOTE: The URLs in the well-known metadata served by each PEP must match the configured, externally reachable URLs, including any non-standard ports. When using `backend-only`, adjust `resource` and `authorization_servers` as needed in `infra/docker/backend/zeta/well-known-backend-only/oauth-protected-resource` (VSDM) and `infra/docker/backend/zeta-popp/well-known-backend-only/oauth-protected-resource` (PoPP). Both paths are relative to the repository root.

=== 3. Optional: Verify the setup with the load test

To check that everything is reachable, run the load test against the local setup:

[source,bash]
----
./mvnw -pl test/vsdm-testsuite/ gatling:test -Dgatling.simulationClass=de.gematik.ti20.vsdm.test.load.VsdmBackgroundLoadSimulation -Dconfig=simulation.conf
----

=== PoPP

The same steps can be applied analogously for the PoPP ZETA ingress:

* Add `popp-zeta-ingress` to `/etc/hosts`, e.g. `127.0.0.1       popp-zeta-ingress`
* Adjust the port via `PORT_POPP_ZETA_INGRESS` in `infra/docker/.env-local` if required.

NOTE: A host port can only be bound once. If both ingresses are needed at the same time, they cannot both be mapped to port 443.

=== ZETA SDK usage

The usage of the ZETA SDK can be seen in the existing `vsdm-client-simservice-java` implementation.
The class `ZetaSdkClientAdapter.java` uses the client, while `VsdmZetaSdkClientConfig.java` configures it.
