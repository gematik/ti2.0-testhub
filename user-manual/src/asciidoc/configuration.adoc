
== Configuration

=== Port Configuration via `.env` File

`doc/docker/.env` contains the default port mappings from the container to the
host. Docker Compose automatically loads this file when you run commands from
the `doc/docker/` directory (or pass `-f doc/docker/compose-local.yaml`).

To remap a port that conflicts with another service on your machine, either edit
`doc/docker/.env` directly or pass the variable inline:

[source,bash]
----
# Remap VSDM server to port 19130 for this run only
PORT_VSDM_SERVER=19130 docker compose -f doc/docker/compose-local.yaml --profile full up -d

# Or export the variable in your shell session
export PORT_VSDM_SERVER=19130
docker compose -f doc/docker/compose-local.yaml --profile full up -d
----

The Spring Boot `application-local.yaml` files in the client services reference
the same port variables (e.g. `${PORT_VSDM_ZETA_PEP:9120}`), so the service URLs
used during local development automatically stay in sync with the Docker setup.
If you run a client service directly from IntelliJ or the command line, you can
load the variables from `.env` in one of two ways:

- **IntelliJ:** Open *Run → Edit Configurations*, switch to the **EnvFile** tab,
  click `+` and select `doc/docker/.env`. All port variables are then available
  to the Spring Boot process.
- **Shell:** Source the file before starting the application:
+
[source,bash]
----
export $(grep -v '^#' doc/docker/.env | xargs)
./mvnw spring-boot:run -pl client/vsdm-client-simservice-java -Dspring-boot.run.profiles=local
----

=== Environment Variables

Each service can be configured via environment variables. Key configuration options:

==== ZETA PDP Services

- `AUTHZ_SEC_STORE_PATH` - Path to PKCS12 keystore file
- `AUTHZ_SEC_STORE_PASS` - Keystore password
- `AUTHZ_SEC_KEY_ALIAS` - Key alias in keystore
- `AUTHZ_SEC_KEY_PASS` - Private key password

==== Client Services

- `POPP_HTTP_URL` - PoPP service HTTP URL
- `VSDM_RESOURCE_SERVER_URL` - VSDM service HTTP URL

=== Test Environment Configuration via `.env` File

Reference additional `.env` files to overwrite default settings from `doc/docker/.env`:

```shell
docker compose -f ./doc/docker/compose-local.yaml \
    --env-file=./doc/docker/.env \
    --env-file=./doc/docker/env-private/.my-own.env \
    --profile ps-only
```

Refer to https://docs.docker.com/compose/how-tos/environment-variables/[Docker's
documentation on environment variables] for more information.

=== Docker Compose Profiles

The Testhub supports different startup profiles for various use cases:

[cols="1,3", options="header"]
|===
| Profile
| Description

| `full`
| Backend + Tiger-Proxies + Clients via proxy. Use this for normal development and testing.

| `perf`
| Backend + Tiger-Proxies + Clients with direct backend access. Use this for performance testing as it bypasses the Tiger-Proxy.

| `backend-only`
| Backend services only (no Tiger-Proxies, no clients). Use this when you want to run your own client implementation against the backend.
|===

==== The `full` Profile – Requests via Tiger Proxy

The `full` profile represents the standard development and testing setup.
All traffic between the clients (VSDM Client, Card Terminal Client) and the
backend services is routed through the **Tiger Proxy**, which records every
HTTP request and response for later analysis (see <<_traffic>>).
A second proxy instance – the **TI-Connect Tiger Proxy** – handles the
simulated TI-Connect path.

.Architecture of the `full` profile
image::diagrams/full_profile.png[Architecture diagram showing clients routing traffic through Tiger Proxy to the backend, width=900]

Key characteristics of the `full` profile:

* The Tiger Proxy acts as a man-in-the-middle recorder – requests are visible
  in the Tiger UI and stored in the `.tgr` traffic files.
* All Tiger Proxy instances (frontend, backend, TI-Connect) are started.
* The OpenTelemetry Collector, Prometheus, and Grafana are included for
  observability.
* Suitable for functional feature-testing, debugging, and contract (Pact) verification.

==== The `perf` Profile – Direct Backend Access

The `perf` profile is optimised for **performance and load testing**.
Clients connect **directly** to the backend services, bypassing all Tiger Proxy
instances.  This eliminates the overhead of request recording and proxy
hop latency.

.Architecture of the `perf` profile
image::diagrams/perf_profile.png[Architecture diagram showing clients connecting directly to the backend without Tiger Proxy, width=900]

Key characteristics of the `perf` profile:

* No backend Tiger Proxy is started – traffic is *not* recorded.
* Lower latency and higher throughput than the `full` profile.
* Suitable for measuring baseline performance, stress tests, and benchmarks.

==== Comparison: `full` vs. `perf`

[cols="1,2,2", options="header"]
|===
| Aspect | `full` profile | `perf` profile

| Tiger Proxy
| ✅ Started – records all traffic
| ❌ Not started

| Popp Service
| ✅ Started – all components (Token Generator, Client, Server) are included
| ❌ Not started - only popp-token-generator is included for token generation

| Traffic recording
| ✅ `.tgr` and `.html` files written
| ❌ No recording

| Observability (OTEL / Prometheus / Grafana)
| ✅ Included
| ✅ Included

| Client routing
| Via Tiger Proxy (extra hop)
| Direct to backend

| Latency overhead
| Higher (proxy hop)
| Lower (direct)

| Recommended for
| All test types are technically possible (feature, debugging, Pact, performance, load), but additional proxy hops add overhead and make this profile unsuitable for load-test measurements.
| Performance and load tests. Feature tests do *not* work in this profile.
|===

==== Starting with Profiles

Use Docker Compose with the appropriate profile:

[source,bash]
----
# Build Docker images first
./mvnw clean install -Pdocker -DskipTests

# Start full stack
docker compose -f doc/docker/compose-local.yaml --profile full up -d

# Start with performance profile (clients bypass Tiger-Proxy)
docker compose -f doc/docker/compose-local.yaml --profile perf up -d

# Start backend only (no clients)
docker compose -f doc/docker/compose-local.yaml --profile backend-only up -d

# Stop all containers (all profiles)
docker compose -f doc/docker/compose-local.yaml --profile full --profile perf --profile backend-only down -v
----

=== Selecting the Test Environment

Everything above configures the *services*. This section covers the *test suites*: which backend a
suite talks to, and how the Tiger proxy is set up for it. Two independent switches are involved,
and it helps to keep them apart:

[cols="1,2,3"]
|===
| Switch | Answers | Mechanism

| Tiger profile
| *Which suite* is running
| Derived automatically from the module directory — nothing to type

| `env`
| *Which stage* every product points at
| `-Denv=local\|ru-dev\|ru\|tu`, selects a node in each registry under `tiger/`

| `popp.env` / `vsdm.env`
| Same, but for one product only
| `-Dpopp.env=<stage>` overrides `env` for PoPP alone; likewise `-Dvsdm.env=<stage>`

| `zeta.env`
| Where the *ZETA* suite points
| `-Dzeta.env=<block>`, a full block name in `tiger/zeta-environments.yaml` — see below
|===

`env` is the one switch that matters: it names the *stage*, and PoPP, VSDM and ZETA all follow it.
Only where a single product must deviate does the per-product override come in.

ZETA is the exception in one respect: its override takes a *full block name* (`popp-rudev`,
`vsdm-tu`, `vsdm-rudev`, `custom`) rather than a stage, because two axes meet there — the stage
*and* which of the two ZETA guards is meant (`popp-zeta-*` or `vsdm-zeta-*` in the docker stack).
`local` is the only name that is both a stage and a block, which is why the default `env=local`
reaches ZETA with nothing to type. Running the ZETA suite with `-Denv=ru-dev` or `-Denv=tu`
therefore needs an explicit `-Dzeta.env=<block>`; `PoPpConfig` aborts with a message listing the
available blocks otherwise.

==== The Tiger profile is derived, not typed

`tiger.yaml` sets `lib.defaultProfile` to an expression that takes the name of the current working
directory and strips the `-testsuite` suffix. Maven forks its test JVM with the working directory
set to the module (`${basedir}`), and IDE run configurations do the same, so:

[source,bash]
----
./mvnw -pl test/vsdm-testsuite/ ... verify    # profile "vsdm"
./mvnw -pl test/popp-testsuite/ ... verify    # profile "popp"
----

The profile loads `tiger-<name>.yaml` from the repository root *if that file exists*, and is
skipped silently otherwise. Only `tiger-popp.yaml` currently exists — it adds the extra proxy port
and the route the PoPP suite needs. Override the derived name with `-DcustomProfile=<name>` if you
ever need to.

NOTE: Do not use Tiger's `PROFILE` environment variable or `-Dprofile` for this. That variant
makes a *missing* profile file a hard startup error, whereas `lib.defaultProfile` skips it.

==== Pointing a suite at another environment

[source,bash]
----
# PoPP suite against the RU-DEV PoPP service
./mvnw -pl test/popp-testsuite verify -Dskip.inttests=false -Denv=ru-dev

# ...but keep VSDM local while PoPP goes to RU-DEV
./mvnw -pl test/vsdm-testsuite verify -Dskip.inttests=false -Denv=local -Dpopp.env=ru-dev

# ZETA suite against the local docker mock (env=local is the default)
./mvnw -pl test/zeta-testsuite clean verify -Dskip.inttests=false

# ZETA suite against a one-off target, without adding a new block
./mvnw -pl test/zeta-testsuite clean verify -Dskip.inttests=false \
  -Dzeta.env=custom -Dzeta.server.domain=https://vsdm-test.tk.de
----

Adding an environment means adding a *block* to the relevant registry under `tiger/` — never a new
file, and never a new URL in Java or in a feature file. All three registries are named
`tiger/<product>-environments.yaml` and share one shape: the selectable blocks live under
`<product>.environments.<name>`, and the derived keys the suites actually read (`popp.server.*`,
`vsdm.server.*`, `zeta.server.*`) sit beside them. A block only sets what deviates; an unknown
`env` value falls back to the shared defaults rather than failing.

IMPORTANT: A placeholder such as `${env}` must never appear in an `additionalConfigurationFiles`
filename in `tiger.yaml`. That list throws a `TigerConfigurationException` as soon as the resolved
name is not an existing file, which silently makes whole environments unusable.

==== Selecting VSDM test data

Which card images and IKNR/KVNR feeder a VSDM run uses is a separate concern, configured with
HOCON rather than through the mechanisms above:

[source,bash]
----
./mvnw -pl test/vsdm-testsuite/ verify -Dconfig=private/tk/tiger_tk_test.conf ...
----

See `test/vsdm-testsuite/HOWTO-TEST.md` for the per-environment `.env`/`.conf` matrix.

=== Custom Configuration

To customize service configuration:

1.  Edit `doc/docker/compose-local.yaml` for Docker Compose setup
2. Or create custom `application-<profile>.yaml` files in each service's `src/main/resources` directory
